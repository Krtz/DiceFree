# Cornberg local save slice

This covers the first two local slices of issue #26, following Q1. The design documents
were reconciled from `setup/unity-project` through `4d98a69`. Existing Cornberg geography,
navigation, combat tuning and Q1 remain intact. Two components were added to the
saved scene: persistence on the player and a stable ID on the resurrection anchor.

## Playtest behavior

- First launch creates one primary Echo with internal user and Echo UUIDs and
  starts at the existing emergence path.
- Level, XP, Q1 and the registered anchor autosave. Reopening resumes progression
  at the registered point; an unavailable point falls back to Cornberg.
- Manifestations use the actor definition's stable class ID, not a hard-coded name.
- Completed Q1 remains completed. Loading does not replay XP, level-up rewards,
  defeat credit or quest turn-in rewards.
- Enemy lives, aggro, targets, attack timers, arbitrary coordinates and dungeon
  sessions are transient. New sessions use authored enemy state.

Loading always starts at **full HP**, whether the player saved injured or dead,
as settled in [issue #29](https://github.com/Krtz/DiceFree/issues/29). Loading is
separate from the existing combat Return action, which still restores 50% HP.
Ordinary cooldowns, effects and combat state are not saved. Current attack timers,
commands and selected targets are cleared; enemy sessions start fresh. Ability,
consumable, status-effect and summon systems are not implemented merely to reset them.

Resources reset by default. `ResourceLoadRule` / `ResourcePersistence` provide a
small tested opt-in policy seam: only an explicitly persistent resource is captured;
otherwise its authored initial value is used even if a stale record exists. The
Novice still has no resource. Unresolved resource records remain inertly preserved.
Future durable companions/world-event sources can use separate versioned sections;
no transient companion combat state or buff instances are serialized. Clock domains
and future multiplayer exit grace remain documented design, not new systems here.

## Storage and recovery

Windows uses `Application.persistentDataPath/Profiles/primary-echo.json`.
Editor play uses a separate `EditorProfiles` directory. Runtime `SavePath`,
`Status` and `Revision` expose diagnostics. In Unity Play Mode, open
**DiceFree → Debug → Profile Inspector** for the editor-only, read-only window.
It reports user/Echo UUIDs, schema/revision, last successful write, class/level/XP,
anchor, quest records, primary path, checksum/header and backup status, migration,
recovery, unresolved records and stopped-autosave errors. It refreshes once per
second, makes no writes and is excluded from player builds. Failed commits do not
advance its last-successful revision/time.

Each Echo is one logical revision with schema version, UUIDs, revision number,
UTC timestamp and SHA-256 checksum. Versioned sections hold JSON payloads.
Unknown sections, including future manifestations, round-trip without parsing.
Unresolved or incompatible quest records are retained inertly. An incompatible
authored quest shows a diagnostic rather than indexing an invalid objective or
offering rewards.

Writes flush a candidate then atomically replace the primary on the same local
filesystem. **Three** recent successful primary revisions rotate as backups.
Interrupted candidates are ignored. A corrupt primary loads the first readable
backup; replacing it preserves the corrupt file separately. If all copies are
unreadable, autosave stops and preserves the files. Unsupported schemas are never
silently downgraded to backups. Invalid manifestation state also stops autosave.
An on-screen message identifies stopped autosave; play remains possible.
A write lock and revision/identity check reject stale competing writers. This is
local file protection, not a cloud conflict-resolution implementation.

Durable progression/quest events mark state dirty. A late-frame snapshot captures the whole
manifestation after synchronous XP/quest handlers complete. The provisional
debounce is **0.25 seconds**. Pause and orderly quit flush current state. A crash
inside that window may lose uncommitted progress. Health changes no longer trigger
save writes because current HP is not durable state.

## Real v1 → v2 migration

Echo schema **1 → 2** upgrades supported manifestation records **1 → 2**. It removes
the old HP fraction and introduces an empty explicitly persistent resource-record
array. Class ID, level/XP, anchor and quest records survive. Opaque unknown sections
and unsupported section versions are copied unchanged; unresolved quest records
retain their ID/version/state. No class-name switch is involved.

`Assets/_DiceFree/Tests/Fixtures/echo-v1.json` was generated by the previous pushed
implementation (`4d8a69d`), not by the new serializer. It contains an injured test
manifestation, completed Q1 and an unresolved quest. Migrations run on detached
data; loading does not replace the original. The next successful atomic save
retains the original v1 primary as a backup. A corrupt current primary can recover
and migrate a v1 backup. Failed migrations stop safely without writing or silently
substituting an older revision. Already-current saves are unchanged by migration.

## Boundaries

`ExperienceProgression` and `QuestJournal` validate/restore detached records without
file I/O. `ManifestationPersistence` binds them to snapshots. `LocalEchoStore` owns
integrity and recovery. `ResurrectionAnchor` supplies stable identity and
`RespawnAtAnchor` resolves spawn positions and clears player combat/interaction state.

There is still one authored registered anchor. Additional-stone registration,
manifestation switching, profile management, Steam/cloud sync, bank/fork transactions,
multiplayer persistence and Echo deletion remain future work. Unsupported future
versions fail closed until explicit migrations exist.
Unknown fields inside recognized version-1 records are not a general forward-compatible
contract; changed records need new versions. This does not complete issue #26.

## Validation

`CornbergSaveValidation.Run` tests storage and a multi-process save/reload fixture.
Pass a fresh absolute `-diceFreeSaveRoot` directory first, then the same root plus
`-diceFreeVerifyReload` in a second process (injured reload, then dead save), followed
by `-diceFreeVerifyDeadReload` in a third process. A separate fresh root with
`-diceFreeVerifyLegacyReload` tests the checked-in v1 save. Checks cover:

- fresh emergence, level 1 and automatic saves after quest acceptance/XP;
- level/stat restoration without reward replay;
- stage-1, stage-2, ready and completed quest records;
- invalid counts and detached snapshots;
- completed reward idempotency across process restart;
- unknown quest/section preservation and anchor fallback;
- clean player combat state;
- checksum recovery, three backups and interrupted candidates;
- unsupported candidate and stale writer preserving the current revision;
- total corruption failing closed.
- injured/dead/legacy reload at full HP, valid/missing/unnavigable anchor handling;
- actual migration, idempotency, failed migration, v1 backup recovery;
- resource reset/opt-in policy and Profile Inspector data/error accuracy.

Batch runs disable persistence unless an isolated root is explicitly supplied.
Existing traversal/combat/Q1 editor validation entry points also disable persistence
to protect user files and fresh-character fixtures. Invalid root arguments never
fall back to a real profile. The known Unity SearchDatabase exception remains #17.

First-slice validation on 2026-09-29 passed: both persistence process runs, the existing Q1
suite, combat/death/well suite and all 13 traversal routes. The Windows development
build succeeded (171,933,258 bytes). Two 12-second standalone launches against an
isolated profile produced revisions 1 and 2 with unchanged user/Echo identities
and no runtime/navigation errors. This is startup/reload smoke coverage, not a
complete standalone quest playthrough. Navigation and tuning assets are unchanged;
the scene diff adds 28 lines and removes none.

All checks passed on 2026-09-29: fresh profile, injured reload, saved-dead reload,
real v1 fixture migration in Play Mode, storage recovery/stale-writer checks,
resource policy and inspector diagnostics (including stopped autosave and the last
successful revision). Load validation establishes an attack target/cooldown before
resetting it, and checks valid, missing and unnavigable anchors. Existing Q1,

12-second standalone launches passed without runtime/navigation errors: fresh
profile revisions 1 → 2 and migrated legacy revisions 5 → 6 → 7, preserving each
Echo identity. The inspector's detached data model is tested; these checks do not
claim manual visual inspection of its editor window or a full standalone quest run.
